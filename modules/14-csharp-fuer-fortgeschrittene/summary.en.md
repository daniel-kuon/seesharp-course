# C# for Advanced Users: Null Safety, Pattern Matching, Span

Chapter 15 (page 949) lists language features that help detect errors early and keep code short and concise: the compiler monitors `null` values, patterns replace branch chains, and spans avoid copies.

## Zero Certainty (15.1, pp. 949–971)

When **the nullable context** is enabled (`<Nullable>enable</Nullable>`), a reference type is considered non-null: `string` cannot accept `null`, whereas `string?` can (15.1.1). There is no difference at runtime; the marking is information for the compiler. **Nullability analysis** determines whether each expression is “possibly null” or “non-null” and issues warnings when null is assigned to a non-nullable variable or when a potentially `null` value is accessed (15.1.2, page 953). Warnings are resolved through code: check, use `?` types, or model the code differently. The **null-suppression operator** `!` (15.1.2.2, page 955) merely suppresses the warning and is permitted if you can justify its use. With `<WarningsAsErrors>nullable</WarningsAsErrors>` (15.1.3.3), null warnings become errors.

When the analysis fails to recognize the relationship, attributes can help (15.1.4, page 962): `[NotNullWhen(true)]` describes an `out` parameter that is non-null only if the return value is `true` (the pattern behind `TryParse`); `[NotNullIfNotNull("s")]` specifies that the return value is non-null if the argument `s` is non-null. In addition, there are the operators (15.1.5, page 968): `?.` and `?[ ]` terminate on `null`, `??` returns a default value, and `??=` assigns only if the left-hand side is null. New in C# 14 is the **null-conditional assignment** `k?.Alter = 5;`: the assignment and the right-hand side are executed only if `k` is not null.

## Pattern Matching (15.2, pages 971–988)

Patterns describe the shape of a value and appear after `is` and in `switch` expressions. There are **constant patterns** (`null`, `0`, `"DE"`), **type and declaration patterns** (`string s`, 15.2.3), **relational patterns** (`< 13`, `>= 18`, 15.2.8), and the combinators `and`, `or`, `not` (15.2.9); `not` binds more strongly than `and`, and `and` more strongly than `or`. **Property patterns** (`{ Elektro: true }`, 15.2.4) check properties and are null-safe; extended property patterns are written as `{ Halter.Land: "DE" }`. The **`var` pattern** (15.2.5) captures a partial value in a variable, **positional patterns** (15.2.7) use `Deconstruct` (every record has one), **tuple patterns** (15.2.6) evaluate several values at once, and **list patterns** (15.2.10, page 985) describe arrays and lists (`[1, .., 9]`, `[var kopf, .. var rest]`). With `when`, you attach an arbitrary condition to each arm. In `switch` expressions, the order decides: The first matching arm wins, and the compiler reports unreachable or missing cases.

## ref, Span, et al. (March 15 to June 15, pages 988–1012)

A `ref` return (15.3, page 988) returns a reference to a memory location instead of a value; `Hoechster(a) = 0;` then writes to the array. `ref readonly` eliminates the need to copy large structures. `Span<T>` and `ReadOnlySpan<T>` (15.4, page 991) are windows into existing memory (array, string, stack): slices do not copy anything, and a single parameter type works for all sources. These are `ref struct` types and exist only on the stack. Since C# 14 (15.4.3, page 994), arrays and strings are implicitly converted to `Spans`, even when used as recipients of extension members in `extension` blocks. An **inline array** (15.5, page 1005) is a struct containing a fixed array declared within itself using `[InlineArray(n)]`. With **collection-type series parameters** (15.6, page 1008), `params` may also take `ReadOnlySpan<T>`, `IEnumerable<T>`, or `List<T>`, replacing many overloads.
